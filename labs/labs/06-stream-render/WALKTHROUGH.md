# Разбор: Рендер стримингового текста

Ответ модели приходит потоком дельт (delta, кусок текста из события `text_delta`, как в лабе 02), 50-200 штук в секунду. Наивный чат на каждую дельту делает `setText((prev) => prev + delta)` и рендерит весь markdown заново. Пока ответ короткий, этого не видно. На длинном ответе каждая дельта стоит всё дороже: парсинг всего текста, reconciliation (сверка нового дерева React со старым), commit (применение изменений к DOM), а потом браузер пересчитывает layout (геометрию блоков) и рисует. Кадр при 60 Гц длится около 16 мс, и когда работа не влезает в кадр, страница дёргается (jank, пропущенные кадры), а ввод в поле лагает.

Ментальная модель: три отдельных решения, и каждое это маленькая чистая функция. Когда рендерить: не чаще раза в кадр (`createDeltaBuffer`). Что рендерить заново: только живой хвост, законченные блоки не трогать (`splitStable`). Куда скроллить: вниз, только если пользователь и так был внизу (`createScrollFollower`). React, DOM и `requestAnimationFrame` (rAF: «вызови этот колбэк прямо перед следующим кадром») остаются снаружи. Время приходит через `schedule`, размеры через аргументы, поэтому всё проверяется тестами в Node, а в браузере подключается в несколько строк.

```ts
import { createDeltaBuffer, splitStable } from './stream-render'

declare function setText(text: string): void // setState стримящегося сообщения

const buf = createDeltaBuffer({
  // в браузере кадр это requestAnimationFrame, а отмена кадра это cancelAnimationFrame
  schedule: (cb) => {
    const id = requestAnimationFrame(cb)
    return () => cancelAnimationFrame(id)
  },
  onFlush: (text) => setText(text), // один setState на кадр, а не на токен
})

buf.append('## План\n\nСначала ') // дельты из collectMessage лабы 02
buf.append('замер, потом **memo**')

// в рендере сообщения:
const { blocks, tail } = splitStable('## План\n\nСначала замер, потом **memo**')
// blocks: ['## План\n\n'], tail: 'Сначала замер, потом **memo**'
```

В React `blocks` рендерит `memo`-компонент с `key` по индексу блока: блоки только дописываются, поэтому индекс стабилен, а проп это строка, и поверхностное сравнение `memo` работает без всяких `useMemo`. `tail` рендерит отдельный компонент, и только он парсит markdown каждый кадр. Скролл решается после commit: одно чтение размеров, одна запись `scrollTop`.

## Шаг 1. Буфер: append копит, кадр сбрасывает

`append` не рендерит и не склеивает весь текст: он кладёт дельту в массив `parts` и, если кадр ещё не запланирован, планирует его через `schedule`. Флаг `scheduled` гарантирует один кадр на любое число дельт: второй, сотый, двухсотый `append` до кадра просто дописывают в массив. Кадр (функция `flush`) склеивает накопленное одним `join`, дописывает к общему тексту и зовёт `onFlush(весь текст, новая часть)`. Весь текст нужен рендеру, новая часть пригодится, например, для озвучки или подсчёта символов. Без буфера 200 токенов в секунду это 200 рендеров в секунду, с буфером не больше 60, сколько бы токенов ни пришло.

```ts
export function createDeltaBuffer({ schedule, onFlush }: DeltaBufferOptions): DeltaBuffer {
  let parts: string[] = [] // дельты с прошлого кадра
  let text = ''
  let scheduled = false

  function flush() {
    scheduled = false
    const delta = parts.join('')
    parts = []
    text += delta
    onFlush(text, delta)
  }

  return {
    append(delta) {
      parts.push(delta)
      if (scheduled) return // кадр уже ждёт, он заберёт и эту дельту
      scheduled = true
      schedule(flush)
    },
    end() {}, // шаг 3
    cancel() {}, // шаг 4
  }
}
```

**Зеленеют тесты:** «append не рендерит: 200 дельт до кадра → один schedule и один onFlush», «следующая порция планирует новый кадр».

**Ловушка:** звать `schedule` на каждый `append`. Тогда 200 колбэков выстроятся в очередь на один и тот же кадр: первый сбросит всё, остальные 199 сделают пустые `onFlush`, а каждый пустой `setState` это ещё один лишний рендер.

## Шаг 2. Нечего показать: кадр не нужен

Пустая дельта ничего не меняет на экране, поэтому планировать ради неё кадр незачем, и рендерить тот же текст тоже. Вторая проверка в самом `flush`: если к моменту кадра новых дельт нет (так будет, когда `end()` из шага 3 уже всё сбросил), он ничего не делает. Чат без новых данных не должен крутить кадры и рендеры впустую: это батарея ноутбука и лишняя работа главного потока.

```ts
function flush() {
  scheduled = false
  if (parts.length === 0) return // новых дельт нет: ни join, ни onFlush
  const delta = parts.join('')
  parts = []
  text += delta
  onFlush(text, delta)
}

// в append, первой строкой:
// if (delta === '') return
```

**Зеленеют тесты:** «нечего показать → кадр не планируется».

## Шаг 3. end(): поток кончился, остаток сразу

`end()` значит «поток закончился нормально»: остаток надо показать сразу, а не ждать кадр. Это не только про 16 мс: в фоновой вкладке `requestAnimationFrame` не вызывается вовсе, и без `end()` хвост ответа висел бы, пока пользователь не вернётся. Запланированный кадр после этого не нужен, его надо снять. Для этого `schedule` возвращает функцию отмены, как пара `requestAnimationFrame` и `cancelAnimationFrame`, и мы её запоминаем в `cancelFrame`. Флаг `closed` выключает буфер насовсем: дельты после конца игнорируются.

```ts
let cancelFrame: (() => void) | null = null
let closed = false

const buffer: DeltaBuffer = {
  append(delta) {
    if (closed || delta === '') return // после конца буфер выключен
    parts.push(delta)
    if (scheduled) return
    scheduled = true
    cancelFrame = schedule(flush) ?? null // запоминаем, чем снять кадр
  },
  end() {
    if (closed) return
    cancelFrame?.() // кадр больше не нужен
    flush() // остаток сразу
    closed = true
  },
  cancel() {}, // шаг 4
}
```

**Зеленеют тесты:** «end() сбрасывает остаток сразу, без кадра, и снимает запланированный кадр».

**Ловушка:** решить, что `end()` не нужен, раз кадр и так запланирован. В фоновой вкладке этот кадр не наступит, и всё, что читает state по концу потока (сохранение сообщения, подсчёт символов, кнопка «Повторить»), увидит текст без последних токенов.

## Шаг 4. cancel(): Stop и unmount

`cancel()` значит «пользователь нажал Stop или компонент размонтирован»: недошедшие дельты выбрасываем, запланированный кадр снимаем, буфер выключаем. И ещё одна страховка в самом `flush`: планировщик может и не уметь отменять кадр (например, ты подставил `setTimeout` и забыл про `clearTimeout`), и тогда устаревший колбэк всё равно сработает. Проверка `closed` в начале `flush` гарантирует, что после отмены не будет ни одного `onFlush`. В React это та самая запись в state после ухода: текст старого ответа попадает в новое сообщение.

```ts
function flush() {
  scheduled = false
  cancelFrame = null
  if (closed || parts.length === 0) return // кадр, который не смогли снять, ничего не делает
  const delta = parts.join('')
  parts = []
  text += delta
  onFlush(text, delta)
}

// метод cancel() в объекте буфера:
function cancel() {
  if (closed) return
  closed = true
  cancelFrame?.()
  cancelFrame = null
  scheduled = false
  parts = []
}
```

Теперь важен порядок в `end()` из шага 3: сначала `flush()`, потом `closed = true`. Наоборот `flush` увидит `closed` и ничего не покажет.

**Зеленеют тесты:** «cancel() (Stop или unmount): кадр снят, после отмены ни одного onFlush», «планировщик не умеет отменять кадр: устаревший кадр после cancel всё равно ничего не сбрасывает».

**Ловушка:** в React забыть `cancel()` в cleanup эффекта. Пользователь переключил чат посреди ответа, а запланированный кадр дописал хвост старого ответа в state нового экрана.

## Шаг 5. splitStable: целые строки и абзацы

Теперь что рендерить. Перепарсинг всего markdown на каждый кадр это O(n²) на весь ответ (KILL билета 20). Но markdown состоит из блоков (абзацы, списки, блоки кода), и блок, после которого уже начался следующий, больше не изменится. Значит, текст можно разрезать на законченные `blocks` и живой `tail`: блоки парсятся один раз и мемоизируются, каждый кадр парсится только хвост.

Главное правило: решают только целые строки, то есть с `\n` на конце. Недописанная последняя строка всегда в хвосте: в ней может быть `**Важно: не` без пары или `[ссылка](https://exa` без скобки, и что из неё выйдет, неизвестно. Целая пустая строка закрывает абзац. Одиночный `\n` абзац не закрывает: в markdown это перенос внутри того же абзаца.

Резать будем не через `split`, а позициями: `start` это начало текущего, ещё не законченного блока, `cut(end)` отрезает блок до `end`. Так ничего не теряется, и выполняется инвариант (условие, которое верно всегда): `blocks.join('') + tail` равно исходному тексту. Флаг `hasContent` нужен, чтобы пустые строки подряд не превращались в пустые блоки: они уходят в начало следующего блока.

```ts
const BLANK = /^[ \t]*$/

export function splitStable(markdown: string): StableSplit {
  const text = markdown
  const blocks: string[] = []
  let start = 0
  let hasContent = false
  let pos = 0
  const cut = (end: number) => {
    blocks.push(text.slice(start, end))
    start = end
    hasContent = false
  }
  while (true) {
    const nl = text.indexOf('\n', pos)
    if (nl === -1) break // последняя строка не дописана: она всегда в хвосте
    const line = text.slice(pos, nl)
    if (BLANK.test(line)) {
      if (hasContent) cut(nl + 1)
    } else hasContent = true
    pos = nl + 1
  }
  return { blocks, tail: text.slice(start) }
}
```

**Зеленеют тесты:** «пустая строка закрывает абзац; одиночный \n абзац не закрывает», «недописанный жирный текст или ссылка в конце остаются в хвосте».

**Ловушка:** `text.split('\n\n')`. Разделители пропадают (склейка уже не равна исходнику), пустые строки внутри блока кода режут код пополам, а последний кусок выглядит законченным, хотя его ещё дописывают.

## Шаг 6. Блок кода: внутри ограды ничего не режем

Внутри блока кода пустая строка это часть кода, а не конец абзаца. Пока ограда (fence: строка, которая начинается с трёх и больше обратных кавычек или тильд) открыта, мы ничего не режем: незакрытый блок кода целиком в хвосте, вместе с открывающей строкой. Закрывающая ограда: тот же символ, не короче открывающей, и после неё ничего, кроме пробелов. Как только она дописана, весь блок кода становится готовым блоком, даже если пустой строки после него нет. И наоборот: открывающая ограда закрывает абзац перед собой.

```ts
const FENCE = /^ {0,3}(`{3,}|~{3,})/
let fence: string | null = null // открывающая ограда, пока мы внутри кода

// в цикле, вместо проверки из шага 5:
if (fence) {
  const m = line.match(FENCE)
  const close = m && m[1]![0] === fence[0] && m[1]!.length >= fence.length && BLANK.test(line.slice(m[0].length))
  if (close) {
    fence = null
    cut(nl + 1)
  }
} else if (BLANK.test(line)) {
  if (hasContent) cut(nl + 1)
} else {
  const m = line.match(FENCE)
  if (m && hasContent) cut(pos) // код начался: абзац перед ним закончен
  if (m) fence = m[1]!
  hasContent = true
}
```

**Зеленеют тесты:** «незакрытый блок кода: всё от открывающей ограды в хвосте», «закрытый блок кода становится блоком; недописанная закрывающая ограда ещё не закрывает».

**Ловушка:** считать закрытием любую строку, которая начинается с трёх обратных кавычек. Ограда с названием языка после неё внутри кода это просто текст, а недописанная ограда в последней строке может ещё получить название языка и закрытием не стать. Поэтому закрытие проверяется только на целой строке и без текста после ограды.

## Шаг 7. Списки и CRLF

Пункт списка закончен, когда дописана строка следующего пункта: тогда всё, что было до неё, режем в блок (`cut(pos)`, как перед оградой). Берём только пункты верхнего уровня, без отступа в начале строки: вложенный пункт `  - вложенный` остаётся в блоке родителя, иначе вложенность пропадёт при рендере. Маркер это `-`, `*`, `+` или число с точкой или скобкой, и после него обязательно пробел: `**жирный**` в начале строки пунктом не считается.

CRLF (перевод строки `\r\n`, как в Windows) приводим к `\n` одной заменой в самом начале. Тогда `\r` не попадает в строки, проверка пустой строки работает, а блоки на выходе одинаковые для обоих вариантов. Одиночный `\r` в конце текста (его `\n` ещё не пришёл) не трогаем: он лежит в недописанной строке, то есть в хвосте.

```ts
const LIST_ITEM = /^([-*+]|\d{1,9}[.)])[ \t]/ // пункт верхнего уровня, без отступа

const text = markdown.replace(/\r\n/g, '\n')

// в ветке «не пустая строка» правило из шага 6 расширяется на списки:
const m = line.match(FENCE)
if ((m || LIST_ITEM.test(line)) && hasContent) cut(pos)
if (m) fence = m[1]!
hasContent = true
```

Последний тест лабы проверяет главное свойство: режем каждый префикс настоящего ответа (символ за символом, в LF и в CRLF) и смотрим, что склейка всегда равна тексту, а готовые блоки только дописываются и ни один не меняется. Ровно на этом свойстве держится `memo`: если «готовый» блок однажды поменяется, на экране останется старая версия.

**Зеленеют тесты:** «пункт списка закончен, когда дописана строка следующего», «CRLF режется так же, как LF», «на каждом префиксе потока: blocks + tail = текст, готовые блоки не меняются».

**Ловушка:** разрешить отступ в `LIST_ITEM`. Тогда вложенный пункт отрежется от родителя и отрендерится отдельным списком. Это осознанное упрощение: точный markdown сложнее (например, пустая строка внутри списка делает его «свободным» и меняет отступы у всех пунктов), но для чата важнее, чтобы готовые блоки никогда не менялись.

## Шаг 8. shouldStick: «у низа» с допуском

Теперь скролл. До низа осталось `scrollHeight - clientHeight - scrollTop` пикселей. Сравнивать с нулём через `===` нельзя: при масштабе страницы `scrollTop` бывает дробным (399.5), и пользователь, который стоит в самом низу, никогда не окажется «ровно внизу». Поэтому допуск `threshold`, по умолчанию 40 px. Если контент короче окна, разность отрицательная, и это тоже «внизу».

```ts
export function shouldStick({ scrollTop, scrollHeight, clientHeight, threshold = 40 }: ScrollMetrics & { threshold?: number }): boolean {
  return scrollHeight - clientHeight - scrollTop <= threshold
}
```

**Зеленеют тесты:** «shouldStick: у низа значит до конца не больше threshold; дробный scrollTop и короткий контент тоже у низа».

## Шаг 9. createScrollFollower: решаем по состоянию до роста

Самая частая ошибка автоскролла: после каждого роста контента считать `shouldStick` по новым размерам. Пришёл блок кода на 300 px, до низа стало 300 > 40, и чат перестал следовать за ответом, хотя пользователь ничего не трогал. Правильно хранить состояние `following` («следуем за низом») и менять его только по событиям прокрутки. Рост контента это решение не меняет, а только спрашивает: следуем? Тогда вернуть позицию низа, иначе `null`, не трогать. Новые размеры нужны только чтобы посчитать, где теперь низ.

Вторая тонкость: наша же прокрутка вниз тоже присылает событие `scroll` (эхо), и иногда уже после того, как текст снова вырос. По размерам такое эхо выглядит как «пользователь не у низа». Отличить просто: пользователь, который уходит читать, крутит вверх, и `scrollTop` уменьшается, а наше эхо его только увеличивает. Значит, отлипаем только когда `scrollTop` стал меньше прошлого и мы не у низа. Вернулся к низу сам: снова следуем.

```ts
export function createScrollFollower({ threshold = 40 }: { threshold?: number } = {}): ScrollFollower {
  let following = true // новый ответ начинается внизу
  let lastTop = 0

  return {
    onUserScroll(m) {
      if (shouldStick({ ...m, threshold })) following = true
      else if (m.scrollTop < lastTop) following = false // только прокрутка вверх
      lastTop = m.scrollTop
    },
    onContentGrow(m) {
      return following ? Math.max(0, m.scrollHeight - m.clientHeight) : null
    },
    following: () => following,
  }
}
```

В браузере `onContentGrow` зовётся один раз за кадр после commit: в `useLayoutEffect` после `setText` или в колбэке ResizeObserver (наблюдатель за размером контейнера). Там одно чтение размеров и одна запись `scrollTop`. Читать `scrollHeight` после каждой записи текста это layout thrashing (пробуксовка раскладки, билет 45): каждое чтение после записи заставляет браузер синхронно пересчитать геометрию.

**Зеленеют тесты:** «был у низа → после роста скроллим в самый низ, даже если пришёл большой кусок», «ушёл вверх читать → новый текст его не дёргает; вернулся к низу → снова следуем», «эхо нашего scrollTo пришло, когда текста уже стало больше».

**Ловушка:** `onContentGrow(m) { return shouldStick(m) ? ... : null }`. На коротких тестовых ответах работает, а на первом же большом блоке кода чат молча перестаёт следовать за ответом.

## Собираем целиком

Вот эталон `solutions/stream-render.ts` целиком, с короткими комментариями к неочевидным местам.

```ts
/** Планировщик кадра. В браузере: cb => { const id = requestAnimationFrame(cb); return () => cancelAnimationFrame(id) } */
export type Schedule = (cb: () => void) => (() => void) | void

export type DeltaBufferOptions = {
  schedule: Schedule
  onFlush: (text: string, delta: string) => void // text: весь текст на сейчас, delta: что пришло с прошлого кадра
}

export type DeltaBuffer = {
  append: (delta: string) => void
  end: () => void
  cancel: () => void
}

export function createDeltaBuffer({ schedule, onFlush }: DeltaBufferOptions): DeltaBuffer {
  let parts: string[] = [] // дельты с прошлого кадра; append только кладёт сюда
  let text = ''
  let scheduled = false
  let cancelFrame: (() => void) | null = null
  let closed = false

  function flush() {
    scheduled = false
    cancelFrame = null
    // closed: кадр, который планировщик не смог снять, после cancel/end ничего не делает
    if (closed || parts.length === 0) return
    const delta = parts.join('')
    parts = []
    text += delta
    onFlush(text, delta)
  }

  return {
    append(delta) {
      if (closed || delta === '') return
      parts.push(delta)
      if (scheduled) return // кадр уже ждёт, он заберёт и эту дельту
      scheduled = true
      cancelFrame = schedule(flush) ?? null
    },
    end() {
      if (closed) return
      cancelFrame?.()
      flush() // остаток сразу: поток кончился, ждать кадр незачем
      closed = true
    },
    cancel() {
      if (closed) return
      closed = true
      cancelFrame?.()
      cancelFrame = null
      scheduled = false
      parts = []
    },
  }
}

export type StableSplit = {
  blocks: string[] // законченные блоки: больше не меняются, их можно мемоизировать
  tail: string // живой хвост: только его парсим и рендерим заново каждый кадр
}

const FENCE = /^ {0,3}(`{3,}|~{3,})/
const LIST_ITEM = /^([-*+]|\d{1,9}[.)])[ \t]/ // пункт списка верхнего уровня, без отступа
const BLANK = /^[ \t]*$/

/** blocks.join('') + tail === markdown с \r\n, заменёнными на \n. */
export function splitStable(markdown: string): StableSplit {
  const text = markdown.replace(/\r\n/g, '\n')
  const blocks: string[] = []
  let start = 0 // начало текущего, ещё не законченного блока
  let hasContent = false // в текущем блоке есть что-то кроме пустых строк
  let fence: string | null = null // открывающая ограда, пока мы внутри блока кода
  let pos = 0

  const cut = (end: number) => {
    blocks.push(text.slice(start, end))
    start = end
    hasContent = false
  }

  while (true) {
    const nl = text.indexOf('\n', pos)
    if (nl === -1) break // последняя строка не дописана: она всегда в хвосте
    const line = text.slice(pos, nl)
    const next = nl + 1

    if (fence) {
      // внутри кода ничего не режем, ждём закрывающую ограду: тот же символ, не короче, без текста после
      const m = line.match(FENCE)
      const close = m && m[1]![0] === fence[0] && m[1]!.length >= fence.length && BLANK.test(line.slice(m[0].length))
      if (close) {
        fence = null
        cut(next)
      }
    } else if (BLANK.test(line)) {
      if (hasContent) cut(next) // пустая строка закрывает абзац; пустые строки подряд уходят в следующий блок
    } else {
      const m = line.match(FENCE)
      // новый блок кода или новый пункт списка закрывают то, что было до них
      if ((m || LIST_ITEM.test(line)) && hasContent) cut(pos)
      if (m) fence = m[1]!
      hasContent = true
    }
    pos = next
  }

  return { blocks, tail: text.slice(start) }
}

export type ScrollMetrics = { scrollTop: number; scrollHeight: number; clientHeight: number }

/** Пользователь у низа: до конца прокрутки не больше threshold пикселей. */
export function shouldStick({ scrollTop, scrollHeight, clientHeight, threshold = 40 }: ScrollMetrics & { threshold?: number }): boolean {
  return scrollHeight - clientHeight - scrollTop <= threshold
}

export type ScrollFollower = {
  onUserScroll: (m: ScrollMetrics) => void
  onContentGrow: (m: ScrollMetrics) => number | null
  following: () => boolean
}

export function createScrollFollower({ threshold = 40 }: { threshold?: number } = {}): ScrollFollower {
  let following = true // новый ответ начинается внизу
  let lastTop = 0

  return {
    onUserScroll(m) {
      if (shouldStick({ ...m, threshold })) following = true
      // отлипаем только от прокрутки ВВЕРХ: эхо нашего же scrollTo вниз сюда не попадает,
      // даже если пока оно летело, текста стало больше
      else if (m.scrollTop < lastTop) following = false
      lastTop = m.scrollTop
    },
    onContentGrow(m) {
      // решение по состоянию ДО роста: большой кусок текста не повод перестать следовать
      return following ? Math.max(0, m.scrollHeight - m.clientHeight) : null
    },
    following: () => following,
  }
}
```

## Как рассказать на интервью

> Ответ модели стримится в чат токен за токеном. На длинных ответах страница начинает тормозить: ввод лагает, скролл дёргается, а пользователя, который проскроллил вверх почитать, тянет вниз. Как сделать это производительным? Что измеряешь и что меняешь?

- Сначала замер. Пишу стрим длинного ответа в React Profiler и в панели Performance: сколько коммитов, сколько длится самый долгий, есть ли long tasks (задачи дольше 50 мс) и фиолетовые блоки layout внутри кадра. Почти всегда картина одна: коммит на каждый токен, и каждый коммит парсит весь markdown заново.
- Когда рендерить. Дельты из потока кладу в буфер, `append` ничего не рендерит, а сброс идёт раз в кадр через `requestAnimationFrame`: один `setState` на кадр, сколько бы токенов ни пришло. На конце потока `end()` сбрасывает остаток сразу, на Stop и unmount `cancel()` снимает кадр, чтобы ничего не записалось в state после ухода.
- Что рендерить. Текст режу на законченные блоки и живой хвост: решают только дописанные строки, пустая строка закрывает абзац, внутри незакрытого блока кода ничего не режу. Блоки рендерит `memo`-компонент с `key` по индексу, они парсятся один раз, а каждый кадр парсится только хвост. Так O(n²) превращается в работу, пропорциональную хвосту. Свойство «готовый блок никогда не меняется» у меня проверено тестом на каждом префиксе ответа.
- Скролл. Храню флаг «следуем за низом» и меняю его только по событиям прокрутки: у низа с допуском 40 px значит следуем, прокрутка вверх значит отлипли. Рост контента решение не меняет, поэтому большой блок кода не ломает следование, а читающего вверху не дёргает. Размеры читаю один раз за кадр после commit и пишу `scrollTop` один раз, без layout thrashing.
- Длинная переписка. Сообщения со стабильными `id` и `memo` на строке, так что при стриме рендерится только последнее. Старые сообщения получают `content-visibility: auto` с `contain-intrinsic-size`, а на сотнях сообщений включаю виртуализацию, понимая её цену: измерение высот, прилипание к низу и поиск по странице.
- Если ввод всё ещё лагает, обновление текста помечаю `startTransition`, чтобы React мог прервать рендер ради нажатия клавиши, и проверяю результат тем же замером, что в первом пункте.
