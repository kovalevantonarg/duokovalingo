# 06. Рендер стримингового текста

**Билеты:** 20 Дизайн: streaming chat UI, 41 Производительность, 45 Конвейер рендеринга браузера, 50 Стриминг: SSE, WebSocket, fetch-стримы.

**Задача:** три решения в `src/stream-render.ts`, от которых зависит, тормозит ли чат, пока ответ модели льётся в страницу. `createDeltaBuffer` копит дельты (куски текста из потока) и отдаёт их одним куском раз в кадр. `splitStable` режет накопленный markdown на законченные блоки, которые больше не меняются, и живой хвост, который ещё растёт. `shouldStick` и `createScrollFollower` решают, прокручивать ли чат вниз.

В тестах нет React, DOM и `requestAnimationFrame`: они идут в Node и в Web Worker. Это не упрощение, а суть вопроса с интервью: производительность стримингового чата решается не в JSX, а в том, когда рендерить, что рендерить заново и куда скроллить. Кадры приходят снаружи через `schedule` (в браузере это `requestAnimationFrame`), размеры через аргументы, как `sleep` и `random` в лабе 05.

Как это ложится на React: `onFlush` делает один `setState` на кадр вместо одного на токен. Законченные блоки рендерит `memo`-компонент с `key` по индексу блока: блоки только дописываются, поэтому индекс стабилен, а проп это строка, и поверхностное сравнение работает без `useMemo`. Хвост рендерит отдельный компонент, и только он парсит markdown каждый кадр. Решение про скролл принимается после commit (применения изменений к DOM), одним чтением размеров и одной записью `scrollTop`.

## Edge-кейсы и почему они важны в проде

- **setState на каждый токен.** 50-200 дельт в секунду, и каждая запускает render, reconciliation (сверку нового дерева со старым), commit, а потом в браузере style, layout и paint. Кадр при 60 Гц длится около 16 мс: когда работа не влезает, получаешь jank (пропущенные кадры), а поле ввода лагает. Автоматический батчинг React 18 тут не гарантия: он склеивает то, что успело прийти до ближайшего рендера, а не ровно кадр. Буфер делает один рендер на кадр, сколько бы токенов ни пришло.
- **Перепарсинг всего markdown на каждый токен.** Каждая дельта заново парсит весь текст, то есть суммарно O(n²): ответ в два раза длиннее тормозит в четыре раза. Это KILL билета 20, и на демо он всплывает ровно на длинном ответе. Законченные блоки не меняются, поэтому их парсим один раз, а каждый кадр парсим только хвост.
- **Незакрытый блок кода.** Посреди потока открывающая ограда блока кода (три обратные кавычки) уже пришла, а закрывающая ещё нет. Если резать по пустым строкам не глядя, код развалится на абзацы, а подсветка синтаксиса будет мигать. Пока ограда не закрыта, всё от неё остаётся в хвосте.
- **Готовый блок не имеет права измениться.** Если «законченный» блок потом меняется, `memo` показывает устаревший текст. Поэтому решают только дописанные строки (с `\n` на конце), а недописанная строка, `**жирный` без пары или `[ссылка](` без скобки всегда в хвосте.
- **Layout thrashing (пробуксовка раскладки) в автоскролле.** Записал текст, прочитал `scrollHeight`, записал `scrollTop`, и так на каждый токен: каждое чтение после записи заставляет браузер синхронно пересчитать геометрию. Размеры читаются один раз за кадр после flush, `scrollTop` пишется один раз.
- **Скролл, который дёргает читателя.** Пользователь ушёл вверх перечитать код, а каждый токен тянет его вниз. Следуем вниз, только если он уже был внизу. Решаем по состоянию до роста: большой кусок кода сразу сделал «до низа 300 px», но это не повод перестать следовать. И эхо собственной прокрутки (событие `scroll` от нашего же `scrollTop`) не должно выглядеть как прокрутка вверх.
- **Flush после Stop или unmount.** Пользователь нажал Stop или ушёл в другой чат, а запланированный кадр ещё сработает и запишет текст в чужое или удалённое сообщение. `cancel()` снимает кадр (`cancelAnimationFrame` в cleanup эффекта) и выключает буфер насовсем.
- **Последние токены не ждут кадра.** В фоновой вкладке `requestAnimationFrame` не вызывается вовсе, и без `end()` хвост ответа повис бы до возвращения пользователя. `end()` сбрасывает остаток сразу.

Для интервью: дальше по лестнице идут вещи вне этой лабы. Старые сообщения за экраном получают `content-visibility: auto` (браузер пропускает для них layout и paint) с `contain-intrinsic-size`, чтобы полоса прокрутки не прыгала. На сотнях длинных сообщений нужна virtualization (виртуализация: в DOM только видимые строки и небольшой запас), её цена: измерять строки разной высоты, отдельно решать прилипание к низу и поиск по странице. Буфер можно подключить через `useSyncExternalStore` (подписка компонента на внешний стор), но если хочешь пометить обновление текста как `startTransition` (несрочное, React может прервать его ради ввода), держи текст в `useState`: обновления внешнего стора React всегда делает синхронно.

## Живой эксперимент (по желанию)

```ts
// фейковый поток: 2000 токенов, по одному каждые 5 мс, это 200 токенов в секунду
async function* fakeTokens() {
  for (let i = 0; i < 2000; i++) {
    await new Promise((r) => setTimeout(r, 5))
    yield i % 40 === 39 ? 'конец абзаца.\n\n' : `слово${i} `
  }
}

// A: setState на каждый токен
for await (const t of fakeTokens()) setText((prev) => prev + t)

// B: один setState на кадр
const buf = createDeltaBuffer({
  schedule: (cb) => { const id = requestAnimationFrame(cb); return () => cancelAnimationFrame(id) },
  onFlush: (text) => setText(text),
})
for await (const t of fakeTokens()) buf.append(t)
buf.end()
```

Рендери текст любым markdown-рендерером: сначала весь текст целиком, потом через `splitStable` (блоки в `memo`-компоненте, хвост отдельно). Для каждого из четырёх вариантов запиши стрим в React Profiler и в панели Performance: число коммитов, самый долгий коммит, long tasks (задачи дольше 50 мс). Во время стрима печатай в поле ввода и смотри, как отстаёт ввод. Твои собственные цифры «сколько коммитов было и стало» и «самый долгий коммит до и после» звучат на интервью сильнее любого определения.

## Прод-сценарий (ответь вслух)

> Ответ модели стримится в чат токен за токеном. На длинных ответах страница начинает тормозить: ввод лагает, скролл дёргается, а пользователя, который проскроллил вверх почитать, тянет вниз. Как сделать это производительным? Что измеряешь и что меняешь?
