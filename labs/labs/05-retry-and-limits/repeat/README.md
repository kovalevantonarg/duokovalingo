# Повторение: лимитер и предохранитель вокруг вызова модели

**Задача:** в `src/retry-2.ts` реализуй `createLimiter` и `withBreaker`. Чат поддержки зовёт модель, а провайдер пускает не больше N запросов в секунду: `createLimiter({ ratePerSec, burst })` это token bucket (ведро с жетонами), каждый запрос сначала берёт жетон через `take()`, а если жетонов нет, ждёт в очереди. Когда модель лежит и отвечает 529 раз за разом, нет смысла держать каждого пользователя на четырёх ретраях по 30 секунд: `withBreaker(fn, { failures, cooldownMs })` это circuit breaker (предохранитель), который после N ретраибельных ошибок подряд перестаёт звать модель и сразу бросает `CircuitOpenError`, а UI показывает «модель временно недоступна».

Отличие от лабы: `withRetry` реагирует после сбоя (подождать и повторить), а здесь ты действуешь заранее. Лимитер не даёт упереться в 429, предохранитель не добивает сервис, который уже лежит. Инструменты те же: классификация ошибок из шага 2, время только через `now` и `sleep` из опций (как `sleep` и `random` в шагах 1 и 3), отмена через `signal` из шага 6.

## Что проверяют тесты

- **burst** первые `burst` вызовов `take()` проходят без ожидания.
- **очередь** одновременные `take()` при пустом ведре ждут 500, 1000, 1500 мс при `ratePerSec: 2`: каждый на 1/rate секунды дольше предыдущего.
- **долив** жетоны копятся по `now()`, но в ведро влезает не больше `burst`.
- **отмена** уже отменённый `signal` и отмена во время ожидания дают `AbortError`, а забронированный жетон возвращается в ведро; настоящий `sleep` по умолчанию тоже просыпается по `abort`.
- **closed** результат и ошибки `fn` проходят насквозь как есть; успех обнуляет счётчик ошибок подряд.
- **open** после `failures` ретраибельных ошибок подряд (5xx, 529, 429, сеть) `fn` не вызывается, сразу `CircuitOpenError` с `retryAfterMs`; 4xx и `AbortError` не считаются.
- **half-open** после `cooldownMs` пропускается одна проба: успех закрывает, ретраибельная ошибка снова открывает на полный `cooldownMs`, параллельные вызовы во время пробы получают `CircuitOpenError`.
- **вместе** лимитер внутри предохранителя: пока предохранитель открыт, жетоны не тратятся.

## Подсказки

- Лимитер это шаг 3 наоборот: там ты считал, сколько ждать после ошибки, здесь считаешь, сколько ждать до запроса. Время только из `now()`, ожидание только через `sleep()`, никаких своих `setTimeout` в логике. Для предохранителя возьми `isRetryable` из шагов 2 и 5 как есть.
- Долив делай лениво: храни `tokens` и `last`, в начале `take()` добавь `(now() - last) / 1000 * ratePerSec`, обрежь до `burst`. Предохранитель это три состояния и три переменные: `state`, счётчик ошибок подряд и `openedAt`; плюс флаг `probing`, чтобы в half-open пропустить ровно одну пробу.
- Почти ответ для лимитера: `tokens -= 1` сразу, до первого `await`, даже если уходишь в минус; ждать надо `-tokens / ratePerSec * 1000`; `sleep` и проверку `signal.aborted` после него оберни в `try/catch`, где в `catch` делаешь `tokens += 1` и пробрасываешь ошибку. Для предохранителя: в начале `call` если `open` и `openedAt + cooldownMs - now() > 0`, бросай `CircuitOpenError` с этим остатком, иначе переходи в `half-open`.
