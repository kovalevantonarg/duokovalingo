# 03. Structured output

**Билеты:** 12 Structured output, 38 Граница runtime.

**Задача:** `extract` в `src/extract.ts`. JSON по zod-схеме через принудительный вызов инструмента (`tool_choice: { type: 'tool', name }`): модель обязана ответить вызовом, а аргументы вызова и есть твой JSON.

## Edge-кейсы

- **Валидный JSON не значит правильные данные** (KILL билета 12). Дата покупки в будущем, отрицательная сумма: схема по типам проходит, бизнес-правило нет. Ловит `refine`, и это проверяешь ты, а не модель.
- **Ошибка валидации уходит модели как `tool_result` с `is_error`** и с названием поля. «Invalid JSON» без деталей модель исправить не может, «purchased_at: purchase date cannot be in the future» может.
- **Потолок попыток.** Если модель трижды не справилась, четвёртая попытка обычно тоже не поможет; нужна понятная ошибка, а не бесконечный цикл и счёт.
- **Ответ текстом вместо вызова.** Бывает (например, если `tool_choice` слетел при рефакторинге). `tool_result` тут слать нельзя: ему не на что ссылаться, API ответит 400.
- **`max_tokens` → сразу ошибка, без ретрая.** Повтор с тем же лимитом оборвётся там же, ты просто заплатишь дважды.

Для ответа на интервью: у Anthropic есть ещё structured outputs со `strict`, где схема соблюдается на уровне декодирования. Даже там `refine`-правила остаются на тебе, и именно поэтому этот код не устаревает.

## Живой эксперимент (по желанию)

Возьми 5 настоящих писем-жалоб (можно сочинить с опечатками и двумя заказами в одном письме), прогони `extract` по 10 раз на `claude-haiku-5-5`. Посчитай распределение `attempts`. Цифра «в 4% случаев нужна вторая попытка» звучит на интервью сильнее любого определения.
